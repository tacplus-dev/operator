Audit complete. I read every non-generated Go file under `pkg/` and `cmd/`, the operator's own Helm chart, and cross-checked the Helm v3.17.3 status transitions the reconciler depends on. Findings below are ranked by severity; each is one I traced end to end in the code.

## Security

**1. GitLab registry token lives in a plaintext ConfigMap and a 0644 file.** `pkg/bootstrap/config.go:82-92` strips only PKI and the LLM credential from operator.yaml, leaving `gitlab_registry_token` in it. The operator chart mounts that file from the `schematic-operator-config` ConfigMap (`helm/templates/configmap.yaml`), and `pkg/bootstrap/bundle.go:202` writes it at 0644 while crypto.yaml gets 0600. The export command at `pkg/bootstrap/init.go:285` deliberately scrubs the token, so the code already treats it as a secret. Anyone with `configmaps/get` in the operator namespace gets a registry pull token. Same class as the ConfigMap-vs-Secret issue found earlier today.

**2. Path traversal in remote config templates.** `pkg/bootstrap/init.go:195-206` joins each `opa:` map key from the downloaded template straight onto `services/opa/` with no cleaning and no `.rego` suffix check. A template entry keyed `../kernel.yaml` or `../../crypto.yaml` overwrites kernel delegates or the PKI on the host that runs `init config`. Anyone who can push a release tag to the config-templates repo can rewrite the cluster's trust configuration.

**3. Self-upgrade can point the operator at an image that does not exist.** `pkg/reconciler/reconciler.go:236-243` takes the running container's image, strips the tag, and appends the tag resolved from `registry.gitlab.com`. On clusters that pull from a mirror prefix (the `operator.localImages` case in `helm/values.yaml`), or when the binary reports a fallback tag such as `dev`, the patch produces a repo/tag combination the mirror does not carry. The new ReplicaSet sits in ImagePullBackOff and the rollout never completes.

## Reconciler self-recovery and correctness

**4. A stale pending-install with no history is unrecoverable, forever.** `pkg/reconciler/reconciler.go:493-516` only accepts a `deployed` or `superseded` revision as a rollback target. A fresh cluster whose first install dies between Helm's release-record creation and `deployed` (Spot preemption, OOM) leaves a lone `pending-install` revision. Every reconcile then errors at line 455, nothing ever installs, and Helm itself refuses a new install on the name. `reconciler_test.go:539` codifies this as expected. This is the direct sibling of today's fix; the pending-install case needs a delete-and-reinstall path rather than a rollback.

**5. A stale pending-upgrade whose only predecessor is `failed` is also unrecoverable.** Helm allows upgrading from a failed release (`upgrade.go:232` in v3.17.3), so "install failed, upgrade started, operator died" yields history `[failed, pending-upgrade]`. Line 506 filters on `StatusSuperseded` only, so the failed revision is never chosen and the loop is stuck the same way as finding 4.

**6. No certificate ever gets rotated before expiry.** `pkg/bootstrap/deploycrypto.go:27` mints kernel node, gateway external, and kmaker serving certs with a 1-year TTL. `KernelTLSNeedsRegeneration` (lines 391-414) checks only presence and the SPIFFE SAN, and `EnsureGatewayExternalTLS` (lines 618-621) checks only presence. There is no `NotAfter` comparison anywhere in `pkg/`. Twelve months after `init cluster`, the operator keeps rendering expired leaf certs and fleet mTLS fails with no reconcile error. The same presence-only check means a changed `fqdn` never re-mints the gateway cert.

**7. Kernel scale-up rotates every node's TLS key and leaves the new node without a signing CA.** When `kernel_nodes` grows, `GenerateKernelTLS` (`deploycrypto.go:340-358`) regenerates all node certs, not just the new ones, so every kernel pod rolls. It deliberately leaves `NodeSigningCa` alone, and `deploy.go:444` guards the index, so the added node gets no signing CA. In-cluster the config dir is read-only, the save at `deploy.go:340-344` is swallowed, and the new certs exist only in the in-memory cache. Every operator restart regenerates them again and rolls kernel again.

**8. `deploy.list` is applied to the configs but not to the chart.** `pkg/bootstrap/deploy.go:102-106` filters the topology on the config provider's private copy of the config. The reconciler (`init.go:116`) and the one-shot apply (`generate.go:195`) hand the generator the unfiltered config. A service excluded by the list still gets Deployments and Services, but with no config value, and crash-loops with "data is null or empty".

**9. On-disk config output disagrees with what the chart deploys.** `pkg/bootstrap/configs.go:66` writes `oauth.yaml` only when `optional_services.oauth` is set, but the generator deploys oauth unconditionally (`generator.go:771`). The `letsencrypt` bootstrap config is missing from the map entirely (only the `-service.yaml` companion is written). `generate` then `bundle pack` produces a bundle with no config for those services, and `apply --bundle` starts them empty. The comment at lines 72-78 describes this exact failure for app services.

**10. Registry tag deletion silently downgrades the fleet.** `pkg/upgrade/checker.go:280-291` replaces the cached version with whatever `selectLatest` returns, with no monotonic check. If the newest tag is deleted or the listing is partial, the cache drops, `Notify` fires, and the next reconcile rolls every service back. Related: the pagination at lines 386-392 treats the `Link` URL as absolute, but the registry API returns a relative path, so any repo past 10,000 tags fails to resolve at all.

**11. `gen-backend-tokens` cannot work and its output is never consumed.** `pkg/bootstrap/backend_tokens.go:36-37` declares an empty provider list, so the command always returns "no tokens found". Even if populated, `BackendTokenPolicyDir` is referenced only by that file; `example.go:417-452` loads the entitlements and proxy policy directories but never the backend-token one. The help text documents a feature that does not exist.

**12. The self-upgrade "wait for restart" is not enforced.** `pkg/reconciler/reconciler.go:189-192` skips the service reconcile after patching the operator image, but the 30-second ticker at line 196 reconciles services with the newly resolved tags anyway. The old operator upgrades the fleet before it restarts, contrary to the comment at lines 182-184.

**13. The operator's kernel-identity bootstrap rebuilds crypto it never uses.** `pkg/bootstrap/kernelidentity.go:62` calls `BuildDeployConfigs` without the PKI and kmaker caches, so it mints a throwaway kmaker serving cert, and on a writable config dir it can run `GenerateCrypto` and `SaveCrypto` concurrently with the reconciler's own build. Separately, the kmaker serving cert is regenerated on every operator restart by design (`deploycrypto.go:656-660`), which rolls the kmaker pod each time the operator restarts or self-upgrades.

## Anti-patterns and drift

**14. Dead Deployment template contradicts the live one.** `pkg/helm/generator.go:1160-1233` (`deploymentTmpl`) and `addNamespace` at line 1147 have no callers. The dead template mounts config from a ConfigMap unconditionally and uses `.Values.<name>.image`, which breaks on hyphenated tenant instance names. It will mislead the next person who searches for how Deployments are rendered.

**15. Default namespace is hard-coded in five places.** `reconciler.go:660-663` re-implements the `namespace()` helper at lines 204-209 with a literal instead of `DefaultNamespace`; the same literal appears at `generator.go:963`, `generator.go:1245`, `deploy.go:580`, and `deploy.go:700`. A future change to the default will miss some of them.

**16. Example kernel.yaml embeds an unused private key at 0644.** `pkg/bootstrap/example.go:186-217` mints a "mock-token" TLS chain into `services/kernel.yaml`, which `BuildKernelConfigProto` parses at lines 299-308 and then discards because `deploy.go:443` overwrites `Tls` with the real node cert. It is dead key material in a world-readable file.

Not reported: the gateway external key being present in every kernel bootstrap Secret and the kmaker signing key in the kmaker Secret are both documented and packaged as Secrets, so they are working as intended. The operator chart's RBAC is tightly scoped and I found nothing over-broad there.
